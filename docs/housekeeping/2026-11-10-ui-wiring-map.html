Proposed rules

  1. One Spine. A class, built once in index.kt and registered on the Kraft app with setAttribute, the way Kraft registers popups. Components reach it as spine. No other global object holds state.
  2. Down by stream, up by call. A component subscribes to spine.x.something and changes it with spine.x.doSomething(). It keeps no copy.
  3. Storage belongs to the Spine. Only the Spine's storage code touches the browser's storage. The UI never names a storage object.
  4. What is stored is a data class. Annotated for kotlinx.serialization, in commonMain so a server can share it, one document per section with a version. Special types get a custom serializer. No hand-written JSON.
  5. Libraries get their data through props. klangui and klangscript-ui never see the Spine.
  6. Talk between siblings has two allowed ways. Through the Spine, when the thing said is state or a command others may care about. Through the parent, with props and callbacks, when it concerns only that parent's children. A component reference points only from a parent to its own child.
  7. A component's own state is what may be lost. Anything a user would miss after a reload belongs in the Spine.

Rules 1, 3 and 4 can be checked by the tool once you have decided them: no stateful global outside spine/, no storage reference outside its folder, no hand-written JSON.

An order of work

  1. The Spine as one object. Turn the eight objects in spine/ into parts of one Spine class and register it. Mechanical, one part per step.
  2. One generic stored section. A small class that loads, saves and streams a serializable data class under one key. Convert the sections one at a time, each with a one-time reader for the old keys. The editor settings first, since they are the smallest.
  3. State held in the UI moves in. The visuals, Learn's search, the walkthroughs, the version and fullscreen values.
  4. KLANG-00413 on top. The app's workbench parts and the label callbacks, which remove the values handed down by hand.
  5. The tool becomes a check. With an allow-list for agreed exceptions.

Decisions for you

  • The three "your call" rows. Should the workbench's layout, the output volume and the MIDI setup follow the user or stay with the machine?
  • The look lives in a library. KlangTheme and KlangLookShelf are global state inside klangui, used by 51 files: 20 in the app and 31 in the libraries, most of them sprudel's tool windows. The auto-update switch is the same case. Either the library keeps owning this state and the Spine only stores and restores it, or the state moves to the Spine and the libraries receive it as input. The first is far less work, since 31 library files would otherwise need the look passed in. The second follows rule 5 strictly.
  • Rule 6. Are the two allowed ways for sibling talk the right ones?
  • Where the work is tracked. Steps 1 to 3 fit KLANG-00389. I would keep them there and close this ticket with the map.
