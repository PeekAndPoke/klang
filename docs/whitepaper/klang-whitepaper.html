Part I

What's already there

Everything in this part is built, running, and audible in the demo today. Nothing here is a plan.

01Overview

The shape of the thing

Klang is a live-coding music system. You type code, it makes sound, and it keeps making sound while you edit the code. There is no compile step you wait on and no audio file anywhere in the loop — every sample you hear is computed, in the browser, in real time.

It is four layers stacked on each other, and each one is a separate, independently useful piece of software:

Layer Module What it is
Language klangscript A small scripting language: hand-rolled lexer, parser, tree-walking interpreter, type inference. Sandboxed — no filesystem, no network, no eval.
Patterns sprudel A pattern language in the Tidal/Strudel tradition. Music as pure functions of time. Started as a Kotlin sibling of strudel.cc; has since gone its own way.
Engine audio_be · audio_fe · audio_bridge The Motör. Oscillators, filters, effects, voice lifecycle, mixing. Block-based DSP with a strict frontend/backend split across a thread boundary.
Surfaces klangscript-ui · klangblocks · klang-notebook A CodeMirror editor with real completions and hover docs, a visual block editor with round-trip AST↔blocks, and an interactive notebook.

It is Kotlin Multiplatform: the same code compiles to JS (browser, running the DSP inside a Web Audio worklet) and to the JVM (desktop via javax.sound.sampled, plus an offline WAV renderer). The JVM target is not a toy — it's how songs get rendered to disk and how the benchmark harness measures the engine.

For scale: roughly 230,000 lines of Kotlin across ~1,200 files. In the core modules there is about as much test code as production code — in klangscript and audio_be, noticeably more. Appendix A has the per-module breakdown.

02Scene

The company we keep

A fair question before going deeper: does anyone actually make music this way? They do — including some of the most respected names in electronic music. Aphex Twin has described building many of his sounds in SuperCollider patches. Jonny Greenwood runs Max patches on stage with Radiohead — the stutter effect on "Go to Sleep", a generative patch driving the piano in live performances of "True Love Waits". Autechre built Confield on generative Max processes — in 2001. And 65daysofstatic used TidalCycles in building the generative soundtrack of No Man's Sky — and opened its live premiere with a live-coded piece.

The live-coding scene itself has grown from an in-joke into a movement. Algoraves — club nights where the music is written as code, projected in front of the crowd — have run in more than eighty cities worldwide since 2012, covered by the Guardian, Wired and Mixmag. And its artists are crossing into ordinary music careers: Lil Data live-codes TidalCycles on the PC Music label, from SXSW to Berghain; DJ_Dave builds her sets in Sonic Pi and has toured with JPEGMAFIA and Danny Brown; Alex McLean has played Tidal at Glastonbury and Sónar.

The tools have numbers to match. Sonic Pi counts its downloads in the millions and sits in school computing curricula worldwide. Max — the patch-as-instrument grandfather of all of this — was acquired by Ableton and ships inside the world's dominant electronic-music DAW. Strudel, the browser-based Tidal this project descends from, is lively enough to make the front page of Hacker News. Music-as-code is not a hypothesis — it is a working scene with audiences, labels, classrooms and festivals, and it keeps growing. Klang is not here to replace any of it: the lineage runs Tidal → Strudel → Sprudel, and Appendix B says thank you properly. It is here to develop the idea further — the same pattern-language joy, on a deeper, hand-built synthesis engine.

03Language

KlangScript — the language you type

Songs are written in KlangScript, not Kotlin. The syntax is deliberately JavaScript-shaped so it's instantly readable, but the standard library follows Kotlin conventions — collections behave the way a Kotlin developer expects, not the way JavaScript does.

There is no eval and no host interop hole. The parser and interpreter are hand-written; the interpreter walks the AST. That's a deliberate security boundary: a song is code someone else wrote, and running a stranger's song must never be able to touch the filesystem or the network. Everything a script can reach is explicitly registered from Kotlin.

Registration is generated, not hand-maintained

The bridge from Kotlin into the script runtime is a KSP processor — KSP being Kotlin's compile-time codegen hook. You annotate a Kotlin function or object with @Function / @Method / @Object, and the processor generates the stdlib registration, the type signatures, the completion data, and the hover documentation — all from one source of truth. Adding a DSL function to the engine and having it show up in the editor's autocomplete with the right parameter names is one annotation, not four files.

It has a real module system

Imports and exports work today, JavaScript-shaped: wildcard, selective, aliased, namespaced, with explicit export lists that prevent scope pollution.

That module system is the load-bearing piece for everything in Part II. The import syntax already exists; what doesn't exist yet is where an import is allowed to point.

04Patterns

Sprudel — patterns as functions of time

A pattern is not a list of notes. It is a pure function: give it a time span, it returns the events that happen in that span. Everything else follows from that — fast(2) scales the query, rev() reflects it, every(4, …) switches on the cycle number. Patterns compose because functions compose.

The time in that sentence is measured in cycles. A cycle is the unit of musical repetition — this world's bar — and a pattern repeats every cycle unless told otherwise. Tempo is cycles per second (cps), and arrangement is written in cycle numbers: "the shakuhachi enters at cycle 28" is a line of code you'll meet in §8.

Rhythm is written in mini-notation, a compact string language inside the host language:

Syntax Name Meaning
a b c Sequence Space-separated values split one cycle equally
~ Rest A silent step
[a b] Group Subdivide one slot
<a b c> Alternation One per cycle, rotating
a*4 Fast Repeat inside the slot
a@2 Weight Take 2 relative time units
a(3,8) Euclidean 3 pulses spread over 8 steps
a? Degrade 50% chance of playing
a|b|c Choice Random pick each cycle
a:2 Variant Pick variant 2 of that sound

Nesting is unlimited. Four bars of drums and a chord progression:

The operator surface is wide — time (fast, swing, compress, inside), structure (every, jux, off, chunk, bite, arrange), tonality (scales, chords, voicings, transposition in scale degrees), probability (sometimesBy, degradeBy, seeded randomness), and arithmetic that maps over event values. Continuous signals — sine, perlin, rand — can be fed into any parameter, so a filter cutoff can be an LFO and a pan position can be noise.

Time is fixed-point, not rational

Musical time needs exact thirds, fifths and sevenths as well as exact halves — a triplet inside a cycle must land exactly on the third, forever, with no drift. Rational arithmetic gives you that, and it was the original implementation. It was also a performance disaster on JS, where every gcd and every plus hit BigInt in the hot path.

Time is now a fixed-point value class: CycleTime, with 110,100,480 ticks per cycle — that is 220 × 3 × 5 × 7. Halves down to 1/220, plus thirds, fifths and sevenths and all their products, are all exactly representable. It is an Int under the hood, and the whole class of subdivision-drift bugs disappears by construction.

A bug worth the war story

Structural operators like seq(N)…slow(N) were silently mis-selecting and dropping events whenever N did not divide the tick constant. Once time was exact, arrange and <…> alternation could be fixed to exact integer-cycle selection. There is now a dedicated spec guarding it, because it is exactly the kind of thing that quietly comes back.

05Engine

The Motör — the audio engine

First, vocabulary. Every sounding note is a voice — one running instance of an instrument. The engine has a metaphor and uses it consistently, in the code and in the DSL: a voice is lit by an Ignitor, the instrument's signal graph (§7 builds them). Each voice is routed to a numbered effect bus called an orbit — that's what .orbit(1) in a pattern picks — and the bus itself is a Cylinder. Cylinders can carry a Katalyst, an orbit-level resonator or effect shared by every voice on that bus. Everything sums into the Master. It's a naming convention, but a load-bearing one: it keeps four genuinely different scopes — note, instrument, bus, mix — from collapsing into the word "effect".

Wait — bus, orbit, cylinder?

Same thing, three lineages. Bus is the classical audio-engineering word: a channel several signals mix into, sharing its processing. Orbit is the Tidal / SuperDirt / Strudel word for exactly that, and sprudel keeps it — .orbit(n) — so live coders arriving from strudel.cc feel at home. Cylinder is the Motör's own name for the machinery that implements one — and .cylinder(n) works in a pattern too, as an alias.

This paper says orbit on the pattern side and Cylinder on the engine side. It is the same object either way.

The signal path, and the thread boundary in the middle of it

Three things about that picture worth calling out

The backend is sharded per playback. It is not one global engine. A dispatcher routes every command by playbackId to its own PlaybackEngine, created lazily and disposed when idle. Each one owns its entire render state: its own scheduler, its own cylinders, and its own ignitor and pipeline registries, forked from the shared built-ins. Two songs playing at once on "orbit 1" get independent orbits instead of silently fighting over one. Custom instruments registered by a playback die with it, rather than leaking into the next.

The block size is a tuning parameter, pinned everywhere. 128 frames, in the browser worklet, on the JVM, and in the offline renderer. It is not a performance dial — several engine behaviours are block-derived, including the analog-drift update rate. Raising it to make an offline render faster would change how the render sounds. Pinning it is what makes the offline WAV bit-faithful to what you heard live.

There is always a safety limiter. −1 dB, 20:1, 5 ms lookahead on the summed mix, on every song, whether or not you asked. Any limiter you author on the master is for shaping; peak-catching is already handled. The 5 ms is a real, accepted latency cost.

A house rule that shapes the code

The Motör stays raw. Parameters are not clamped "for safety" unless there is a numerical reason — you can absolutely make it scream. What is guarded is numerical sanity: NaN/Inf guards, denormal handling, and explicit safe bounds in the DSP, because a single NaN in a feedback delay poisons the buffer forever.

06Sources

Oscillators, filters, effects

Every sound source below is hand-written DSP — no wavetables, no samples underneath, no Web Audio nodes doing the work. They're addressable by name from a pattern (.sound("supersaw")) and as builders in the instrument DSL (Osc.supersaw()).

Family Sources
Classic sine, sawtooth, square, triangle, ramp, pulze (variable duty), impulse, and zawtooth — a deliberately naive, aliasing saw, kept because it is brighter and sometimes that's what you want
Unison supersaw, supersine, supersquare, supertri, superramp — N detuned copies with per-voice spread, gain jitter and phase randomisation
Physical pluck (Karplus-Strong, with decay / brightness / pick / stiffness) and superpluck (unison strings)
Noise whitenoise (tiltable), pinknoise (exact −3 dB/oct), brownnoise, perlin / berlin (with fBm octaves and persistence), dust (heavy-tailed, optionally bipolar), crackle (a chaotic map, not a dust alias)
Samples Drum banks, soundfonts, arbitrary URLs — with slicing, looping, and per-hit start positions

Filters: resonant SVF lowpass / highpass / bandpass / notch, one-pole variants, and two resonator banks — body(), which models a passive instrument body (mahogany, rosewood, tube…), and vowel(), a formant filter. Both are blended through a shared parallel-mix filter with a physical floor, so they colour without ever thinning the signal out — a passive body adds no energy and never makes a sound sparse.

Effects: reverb, delay, phaser, compressor, sidechain ducking, distortion with nine shapes and optional oversampling, bitcrush, sample-rate reduction, tremolo, vibrato, FM, pitch envelopes, and per-voice analog drift.

Design position

The sound model is a pencil sketch, not photorealism. An instrument gets two to four real acoustic "tells" — the right waveform family, a breath-noise transient, a material-appropriate cutoff, a pitch scoop — and sparse fill around them. The target is deliberately non-moving: nothing adapts, nothing randomises itself behind your back. You can learn it.

07DSLs

Three DSLs above the engine — and one to come

The pattern language says when and what. Three further DSLs say how, at three different scopes — and the fourth scope is still waiting for its DSL, at the end of this section.

1 · Ignitor DSL — building an instrument

An instrument is a signal graph, composed with ordinary method chaining. Any numeric parameter accepts either a number or another Osc node, which is how you get audio-rate modulation without a separate modulation-routing concept.

To be clear about what runs where: the script builds the graph once, and the graph crosses to the audio thread as data. What you composed is block-based arithmetic — .plus() is a 128-frame buffer add, .times() a buffer multiply — rendered in tight loops over FloatArrays. The interpreter never runs per sample; it only describes the machine.

That Osc.param(name = "punch", default = 24) in the kick is the parameter system: a named slot with a default, overridable per note from the pattern side — and since the override value is itself a pattern, "<24 48>" alternates the drop depth cycle by cycle. The two languages meet exactly there: the instrument declares the knob, the pattern plays it. Osc.variants(a, b, …) bundles several flavours of one instrument into a single sound, selected per event with the same :index suffix that picks sample-bank variants — so seq("0 1 2:1 3:1") can have two notes ring out and two chug, from one instrument.

2 · Pipeline DSL — reordering the voice strip itself

The per-voice chain — filter modulation, crush, coarse, distort, filter, tremolo, phaser, VCA (synth-speak for the amplitude stage the ADSR envelope drives) — is data, not hardcoded order. Two built-ins ship: modern, the classic subtractive order with the amplitude envelope last, and pedal, where the VCA comes early so the envelope drives the waveshapers the way a guitar pedal does. 3 · Master DSL — the whole song's bus

The master chain rides in the pattern stream rather than sitting in global config, which means live edits to it cross-fade instead of clicking, and an offline render reproduces it exactly.

4 · Katalyst DSL — the missing quadrant Designed, not built

The symmetry above has a hole. Per-voice source: Ignitor DSL. Per-voice processing order: Pipeline DSL. Whole-song bus: Master DSL. The fourth scope — the shared effects path on a Cylinder — has the effects but not the authoring surface. Body, vowel, delay, reverb, phaser, compressor and ducking all run at orbit level today; patterns set their amounts, but the chain itself — which effects, in what order — is hardcoded in the engine. The Katalyst DSL closes that quadrant: declare a per-orbit chain the way Pipeline.of(…) declares the per-voice one, following the Master DSL's registration pattern and reusing the same DSP underneath. One word per concept: the Ignitor lights the voice, the Katalyst refines the bus.

The rule that keeps four DSLs coherent

Parameter parity. If a parameter exists on one surface it should exist on all of them, mean the same thing, and use the same scale — and the conversion lives in exactly one place. This is not theoretical tidiness: ignoring it produced a roomSize that was 10× different between the master and an orbit, and that bug was found by ear.

08Real code

A real song, in full

Everything above, used together. This is an actual built-in song — Die Kirschblüte — not a constructed example. Five hand-built instruments, six-part pad voicing, layered entries over 42 cycles.

A few things in there are worth noticing. .orbit(n) assigns an effect bus, and that assignment is architectural — orbit-level effects like body() and reverb are shared by everything on that orbit, so two instruments that each need their own wooden body must be on different orbits. .filterWhen(x => x >= 28) is arrangement as a predicate over the cycle number. And analog(…) threads a single "how much does this drift out of tune" number to five linear destinations at once, seeded so note attacks land in tune and only then wander. The Osc.slot.analog inside the instrument definitions is the receiving end of that thread — the note's analog amount exposed as a slot, so the instrument's own filters drift along with its pitch.

10Internals

Engineering notes

The parts that might interest you as much as the music does. Real-time audio in a browser is a hostile environment: 128 frames at a time, no allocation, no locks, and a JS runtime that boxes things you didn't know were boxed.

No boxed primitives, anywhere in the audio path

On Kotlin/JS, Long is emulated as an object pair, and Char, Short and Byte box. The rule across the project is Int and Double only. This is why time is a fixed-point Int rather than a rational of longs.

The wire codec is generated

Voice data crosses from the main thread into the worklet on every scheduled note. kotlinx.serialization was decoding at ~67 µs per voice, which is not survivable at note density. A second KSP processor now generates a trust-codec directly from the @WireFormat types: 67 µs → 385 ns, about 174×, confirmed in the browser. Protobuf was tried and rejected — it is slow on JS.

Voice data is mutable and single-owner

The immutable-data-class instinct is right until you're cloning a large object per note. The voice parameter object was made mutable with a single owner and grouped into about a dozen sub-objects, so a leaf clone touches only what changed: 820 ns → 47 ns, roughly 17×.

Benchmarks run real songs

There is a harness that compiles actual song source, renders it offline, and reports per-block timing — plus a real-time-factor / voice-count harness for the engine in isolation. That's how it was found that a per-voice effect multiplied by superimpose was the CPU sink in one song, which is why body() moved to orbit level and is now applied once per orbit rather than once per layered copy.

Tests are mutation-checked

A new test isn't accepted because it passes — it is accepted after deliberately breaking the code it covers and confirming it goes red. Mutation-testing tools were evaluated for the DSP and rejected with disassembly evidence: the hot path is fully inlined, so the tooling can't see it. So it's done by hand. Reviews loop until a clean round, and fixes get re-reviewed.

Alongside that: golden-file tests for the pattern language, and dedicated specs guarding every bug class that has bitten twice — cycle-boundary selection, timeshift duplication at cycle boundaries, analog-drift coefficients, sample onset alignment.

Part II

Where the journey might go

Everything from here on is design, not code. Some of it is settled as an idea while being completely unsettled as a mechanism — and where that's true, it's marked.

11Sharing

Import / export Idea set, mechanism open

This is the one I most want argued with, so here it is in full.

The observation. Every other music genre sits on a corpus. Sample-based music literally could not exist without one — producers don't start from a blank page, they start from the breaks. Live coders open empty editors. There is no canon, no "Amen break" of patterns.

The interesting part is that Klang's medium is text, not audio. Which means lineage can be exact rather than anecdotal. If you make something good and it was built from other people's parts, that ancestry is machine-readable — a citation chain, not a rumour. No stem-sharing platform can offer that, because binaries don't compose.

The shape

KlangScript already has imports. The proposal is to let them cross servers:

Reframed honestly: this is not a distributed filesystem, it's a federated package registry — a far better-solved problem. The design cornerstones so far:

Cornerstone Consequence
Immutable tags Republishing @v1.0 is an error, permanently. npm learned this via left-pad; Go enforced it from day one.
Content addressing Every file and blob is referenced by hash; a tag resolves to a manifest of hashes. Caching mostly disappears — fetch once, cache forever, verify locally, so content can come from anywhere.
Flatten at tag time When a version is tagged, the origin resolves the full transitive closure then and writes it into the manifest — a lockfile. An importer needs exactly one conversation to learn everything it must fetch. Hops never cascade at import time.
@latest is edit-time only Publishing pins everything. A song that sounded right yesterday must sound identical today; an unpinned import contradicts that. Resolution is pull with a short TTL, the Go module-proxy model — no webhooks, no subscription registry.
Everything cacheable is immutable Cache invalidation — the hard CDN problem — doesn't exist here. Which is what makes "everyone runs an instance" credible instead of a bandwidth trap: a hobbyist box survives a viral song because the edge eats the traffic and the origin serves each blob once.

Licensing is the mechanism, not the paperwork

Every published asset carries a mandatory license from a small lattice, chosen at publish and stored in the manifest. Three things fall out of that:

  • The license gates importability. Redistribution-permitting → the import button exists. All-rights-reserved → stream-only, no import. Permission and mechanics become the same thing.
  • Restrictions accumulate, checkably. A combined work must satisfy all input licenses at once, so the server computes the effective constraints of the closure at tag time and refuses an incompatible publish. Creative Commons already solved the compatibility chart; a small lattice makes it machine-checkable.
  • Attribution is automatic. The pinned closure is the credits roll — generated from ground truth rather than self-reported.

And because it's mechanical, it's honest by construction. That attribution graph is a citation network in the scientific sense.

The decision this all turns on

The protocol records; it does not score. No likes, no play counts, no follower counts, no leaderboards, no computed reputation, no algorithmic feed. Discovery works the way it works for papers: love something, open its credits, follow the reference to whoever made that bass, browse their catalogue. Pull, not push. A server's catalogue is a library, not a feed.

This isn't only taste. Any in-system honour mechanism recurses — citations reward the roots (samples, presets) and finished songs are sink nodes; answer that with curation-as-citation and you just move the question to who honours the curator. The only termination we can find is outside the system: people. And it has a nice side effect — citation cartels attack scores, so with no scores there's nothing to attack. A viral wave landing here hits a credits page and nothing inside re-amplifies it. You can't stop the wave; you can decline to build the resonance chamber.

Play counts are also structurally impossible, not merely unwanted: edge caching means origins never see most fetches, and the play event is client-side. Counting them would require telemetry in the player — surveillance built into the instrument.

One consequence nobody expects

Klang songs are infinitely long — patterns cycle forever. So a mixtape entry can't just reference a song; it has to specify a cycle window: super-song@v1.0 [cycles 128..192).

Which means making a mixtape is unavoidably authorship. Choosing which cycles are the cycles is the DJ picking the break. Effortless consumption doesn't exist even in principle — the format demands a decision. And because playback re-performs the song live through the engine, with per-voice drift making each pass a fresh performance, a mixtape is closer to sheet music than to tape. Add author-exposed parameters — a song can publish feel: 0..100 with a default and a meaning — and an entry becomes (song@version, cycleWindow, overrides): score, window, and interpretation.

Genuinely open

Identity and migration (server-in-name couples you to your home server — the email problem). Private and unlisted songs. The exact license set. Whether non-commercial licenses are offered at all — they fragment a commons into two incompatible pools and chill exactly the remixing this is meant to encourage; the current lean is to launch without them. And whether any of it should be built before there's evidence anyone wants to remix anything.

12Licence

Open source, and the node idea

Klang Audio Motör is free software under the GNU AGPL v3. The tones module — a Kotlin port of tonal.js — is carved out as MIT, matching upstream. Every file carries an SPDX header; AUTHORS.MD is the authoritative copyright list and CREDITS.MD the list of what this stands on — condensed in Appendix B.

AGPL is chosen deliberately for the network case: if you run a modified Klang server, the modifications are owed back. And to state the thing users need to see in writing — the engine's license does not reach your songs. Songs are user content, not derivative works of the engine.

Anyone can run a node

The intent is that a Klang server is something you install, the way you install a Mastodon or Matrix instance. You run one, it hosts your songs and your samples, and it becomes a node in the network. Your imports resolve through it, and it keeps a durable copy of everything your songs depend on.

That last part is doing real work:

  • Server death is survivable. On cross-server import, your home server vendors the pinned closure — a durable copy, not an evictable cache. Every song is then self-sufficient where it lives. A dead server kills its own songs, never anything downstream. The license gate is what makes that lawful, which is why the two designs are the same design.
  • Liability distributes to operators, the e-mail and Mastodon model. Each operator gatekeeps their own accounts and answers for what they host. A bad server dies here and there; the network shrugs.
  • Policy is the operator's liability dial. Instance settings — bring-your-own samples on or off, open or invite-only registration, quotas, a minimum license floor — live in the discovery document next to protocol capabilities. Curated-samples-only is near-zero exposure; enabling uploads is an accepted moderation burden. Risk appetite becomes a config file, and clients adapt their UI from it.
  • Old versions are supported effectively forever. In a federation every server is also a client of every other server, and the network will always contain unattended instances that never upgraded. The oldest living API version is the lingua franca. Immutability makes that nearly free — old responses are static bytes. The intended enforcement is a public conformance suite with golden wire fixtures, runnable by any third-party implementation.

Which sets a hard constraint on the design: a five-endpoint API that must be right the first time is a much better problem to have than a large one that must be right the first time. The plan is to ship v1 narrower than feels comfortable — additive evolution means yes-later is always possible, unsaying never is.

The intended reference instance is klang.art. It has no special protocol status; it's just the first one.

13Honest

What's rough

This is pre-alpha and it shows. Use Chrome on a laptop or desktop; other combinations are untested and some are bad.

  • The first note of a song can stutter. Expensive per-engine resources — delay rings, cylinders — are allocated on first use, and the spike lands on the first thing you hear. The fix is designed (a self-balancing pool that keeps N warm and refills toward N per render cycle) and not built.
  • Voice eviction doesn't exist. Nothing culls voices under load yet.
  • Many effects are not fully rounded yet. The body and vowel resonators especially are proofs-of-concept — a handful of preset materials, constants tuned by ear, calibration unfinished across instruments and registers. They make the right kind of sound; they don't yet make it everywhere.
  • The frontend and backend clocks can diverge when the worklet stalls — the frontend runs on wall time, the worklet derives time from frames. A sync layer absorbs part of it, not all.
  • Roughly 10× off a native DAW on raw performance. There are ideas for closing that (a native daemon fed control events over a socket; Zig or Rust compiled to Wasm inside the worklet) and they are all deliberately parked until much later.
  • No accounts, no server, no sync. Everything in Part II is unbuilt.

The working order is engine first, then a stretch of tutorials, then whatever launch means, and hard performance work last. Sound before platform — an instrument that sounds like a prototype doesn't get saved by infrastructure.

Where to poke

The demo is at klang.finzo.de — open a built-in song, change a number, hear it change. If you want to read code rather than play with it, the three most interesting files are probably the pattern query machinery in sprudel/src/commonMain/kotlin/lang/, the per-voice strip in audio_be/…/voices/strip/, and the dispatcher in audio_be/…/PlaybackEngineDispatcher.kt.

14Join in

An invitation

This paper is a teaser, and you are reading it because we would like company. Klang has been a two-hands-and-one-AI project so far, and it has reached the stage where more ears and more taste make it better. Some ways in, in roughly ascending order of commitment:

  1. Play with it — and report back, unhinged but constructive. The most useful thing you can tell us is where the abstractions leak: where you tried something reasonable and the system fought you. Second most useful: what surprised you by working.
  2. Write a short song. The built-in corpus is 14 songs; §11 dreams of a canon. Every good thirty-cycle piece extends the initial corpus — and stress-tests the DSL surface in ways no test suite can.
  3. Write tutorials. 38 live tutorials exist (§9), every example playable in the page — but they were written by the people who built the thing, and it shows. If you can explain without assuming, and make a beginner want the next lesson, that is a contribution no amount of engine work replaces.
  4. Author an instrument. The Ignitor DSL (§7) makes an instrument a signal graph. Pick something the roster lacks — a harmonica, a broken church organ, rain on a tin roof — and chase its two-to-four acoustic tells.
  5. Mix and master the built-in songs. They were balanced by ear at the workbench, and the Master DSL (§7) has more to give than we ask of it. Take a song, balance its orbits, stage its master chain — and leave it sounding like a record.
  6. Calibrate by ear. The body and vowel resonators (§13) need exactly the contribution code review cannot give: someone with ears playing real material through them and saying "the mahogany gets boxy above c5". Bring taste, not patches.
  7. Record a sample library. Recorded for Klang, owned by the project — genuine provenance for the day any of this goes public, with no licensing shadow over the default catalogue.
  8. Argue with §11. The federation API intends to freeze v1 the way Go froze Go 1 — every exposed field a forever-promise. The cheapest moment to find the design mistake is before that, which is now. Tell us whether it is a good idea or a beautifully-designed mistake.
  9. Hardcore: plan the Zig backend. §13's ~10× gap has a deliberately parked answer — a native backend fed control events, or Zig compiled to Wasm inside the worklet. The code is for later; the planning can start with PeekAndPoke now. If systems programming at audio rates is your idea of fun, this is the one.

One hint before the bigger ones: talk to the authors first. The engine moves fast, several subsystems are mid-rework, and a short conversation saves a long rebase. Der Weg ist das Ziel — but it is more fun in company.

BCredits

What this stands on

§11 proposes credits as protocol — an attribution graph generated from imports, honest by construction. This project already keeps the habit by hand. What follows is CREDITS.MD, condensed; every layer of Klang has an ancestry, and it is a pleasure to name it.

The lineage
Tidal Cycles — Alex McLean The Haskell live-coding environment that pioneered the cyclic pattern language at the heart of all of this
Strudel The JavaScript reimagining of Tidal. Klang exists because of Strudel — its open code, open samples and documentation were the way in. Lineage: Tidal → Strudel → Sprudel
Switch Angel The YouTube short of a Strudel session that sparked the whole project — and most of the default drum kit's samples (uzu-drumkit): the kicks, snares and hats you hear first are hers
Filters & DSP
Vadim Zavalishin The Art of VA Filter Design — the zero-delay-feedback (TPT) state-variable filter behind lowpass / highpass / bandpass / notch
Andrew Simper — Cytomic The canonical trapezoidal-integrator SVF formulation the implementation follows
Vadim Filatov — Obxd The diode-pair resonance-saturation idea that warms the filters when driven
Jezar at Dreampoint Freeverb — the reverb architecture (public domain)
Karplus & Strong Plucked-string synthesis (pluck, superpluck)
Välimäki et al. PolyBLEP band-limited oscillator anti-aliasing
Adam Szabo How to Emulate the Super Saw — the JP-8000 analysis behind the super-oscillators
Geraint Luff — Signalsmith The lookahead-limiter construction, and the insight that the smoothing must fit inside the lookahead budget
Giannoulis, Massberg & Reiss Digital Dynamic Range Compressor Design (JAES 2012) — the compressor's feed-forward topology
Ken Perlin · Bjorklund · musicdsp.org Perlin noise, Euclidean rhythms, and the public-domain "27/9" fast-tanh in the soft clipper
Hardware inspirations
Roland JP-8000 (1997) The synthesizer that introduced the Super Saw — seven sawtooth oscillators, one centre and six detuned, in a single voice. The sound that defined trance, and the reason a supersaw lives in every live-coding environment today. Klang's super-oscillators chase that sound, by way of Szabo's analysis above; the implementation is its own
Roland TR-808 & TR-909 The drum machines whose voices echo through the bundled sample banks — bank("RolandTR808")
Acoustics — the body-resonator landmarks
Fletcher & Rossing · Benade · Sundberg The Physics of Musical Instruments, Fundamentals of Musical Acoustics, The Science of the Singing Voice — the resonance landmarks behind the wood, violin, bell, brass and croon materials. Everything beyond the landmarks is sparse fill, tuned by ear

Felix Roos chord-voicings (the voicing dictionaries) and dough-samples (curation and hosting of the bundled sample sets)
