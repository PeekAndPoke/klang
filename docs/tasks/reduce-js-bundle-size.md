# Reduce the frontend JS bundle size

_Status: in progress. Step 1 ((b), (c), the cast fix, non-literal defaults refused) committed 2026-10-06 (599540e6);
step 2 ((d), (e), the split per area) done 2026-10-06, awaiting review (see "Step 1 done" and "Step 2 done" at the
end). Created 2026-06-11._

## Problem

The production frontend bundle is too large:

```
build/dist/js/productionExecutable/
  klang-engine.<hash>.js        9.3 MB   ← main bundle (downloaded at initial load)
  235.<hash>.js                 864 KB   ← lazy chunk: pixi.js
  248.<hash>.js                 716 KB   ← lazy chunk: three.js
  klang-worklet.js              244 KB   ← audio worklet (separate)
  *.js.map                       ~21 MB  ← source maps (NOT downloaded by end users)
```

The **9.3 MB `klang-engine.*.js` is the initial-load payload** we want to shrink.

## What is actually in the 9.3 MB (source-map attribution)

Attributing generated bytes back to their source via the source map:

| Source bucket                                                    | Share     | ~Bytes       | Verdict                          |
|------------------------------------------------------------------|-----------|--------------|----------------------------------|
| **`sprudel/build` (KSP-generated)**                              | **36.8%** | **~2.4 MB**  | **Abnormal — the main offender** |
| `sprudel/src`                                                    | 10.7%     | ~0.7 MB      | expected (sprudel runtime)       |

| `@js-joda/core` (+ timezone)                                     | ~3.6%     | ~0.23 MB     | date lib                         |
| klangscript / audio_* / kraft / ultra / app `src`  | the rest  | —            | expected                         |

initial load and are not the problem.

## 1. Primary win — de-bloat the KSP-generated registration (~1.2–1.6 MB)

### Root cause

`sprudel/build/generated/ksp/.../GeneratedSprudelRegistration.kt` is **3.76 MB / 66,015 lines**, produced by
`KlangScriptProcessor`. It registers the whole KlangScript stdlib and emits **~1,578 raw closures** (1,215
`registerExtensionMethodWithSpecs` + 363 `registerFunctionWithSpecs`), each ~28 lines of **near-identical boilerplate**:

```kotlin
) { receiver, args, loc ->
    @Suppress("UNCHECKED_CAST")
    val typedReceiver = wrapAsRuntimeValue(receiver).convertToKotlin(SprudelPattern::class, loc)
    val callInfo = CallInfo(
        callLocation = loc,
        receiverLocation = (receiver as? StringValue)?.location ?: (receiver as? NumberValue)?.location,
        paramLocations = args.map { arg -> (arg as? StringValue)?.location ?: (arg as? NumberValue)?.location },
    )
    checkArgsSize(fn = "firstOf", args = args, expected = 2, location = loc)
    val n =
        convertArgToKotlin(fn = "firstOf", args = args, index = 0, cls = Any::class, nullable = false, loc = loc) as Any
    val transform = convertArgToKotlin(
        fn = "firstOf",
        args = args,
        index = 1,
        cls = Function1::class,
        nullable = false,
        loc = loc
    ) as ((SprudelPattern) -> SprudelPattern)
    wrapAsRuntimeValue(typedReceiver.firstOf(n = n, transform = transform, callInfo = callInfo))
}
```

`CallInfo` build ×1,578, `checkArgsSize` ×1,453, `convertArgToKotlin` ×1,817, the
`(x as? StringValue)?.location ?: (x as? NumberValue)?.location` idiom ×~1,578, function-name string literal ~5× per
closure. All of it is pure mechanical duplication; every registration is reachable so DCE keeps it; it minifies into ~
2.4 MB. (The closure *count* itself — function × receiver type, e.g. `firstOf` for `SprudelPattern`/`StringValue`/
`Function1` — is intended auto-lifting and is **not** changed; only the *per-closure size*.)

### Fix — move the boilerplate into shared runtime helpers; keep only the typed dispatch generated

The emitted `ParamSpec` list already fully describes each parameter (`name`, `kotlinType`, `isNullable`, `isVararg`,
`isOptional`, `default` — verified at `klangscript-ksp/.../KlangScriptProcessor.kt:1643-1652`), so the boilerplate can
be driven from the specs at runtime.

**a) Add runtime helpers** in `klangscript/src/commonMain/kotlin/runtime/NativeInterop.kt` (reuse existing
`checkArgsSize`, `convertArgToKotlin`, `wrapAsRuntimeValue`, `RuntimeValue.convertToKotlin`):

- `extractLocation(v: RuntimeValue): SourceLocation?` — the
  `(v as? StringValue)?.location ?: (v as? NumberValue)?.location` idiom, once.
- `buildCallInfo(receiver: Any?, args, loc): CallInfo` — uses `extractLocation`; `receiver = null` →
  `receiverLocation = null` (top-level).
- `convertArgs(fn, args, paramSpecs, loc): List<Any?>` — does
  `checkArgsSize(fn, args, paramSpecs.count { !it.isOptional }, loc)` then converts `min(args.size, paramSpecs.size)`
  non-vararg specs via `convertArgToKotlin(fn, args, i, spec.kotlinType, spec.isNullable, loc)`. Converting only the
  *present* args reproduces today's "convert optional only when supplied" arity behavior.

**b) Add thin registration wrappers** in `klangscript/src/commonMain/kotlin/builder/KlangScriptExtensionBuilder.kt`,
layered over the existing `registerExtensionMethodWithSpecs` / `registerFunctionWithSpecs`. Provide 4 variants (
extension vs top-level × with/without callInfo — the no-callInfo variant skips `buildCallInfo` to preserve today's
no-allocation path):

```kotlin
fun KlangScriptExtensionBuilder.registerExtMethodFast(
    receiver: KClass<*>, name: String, paramSpecs: List<ParamSpec>, receiverKotlinType: KClass<*>,
    dispatch: (receiver: Any, a: List<Any?>, callInfo: CallInfo) -> Any?,
) = registerExtensionMethodWithSpecs(receiver, name, paramSpecs) { rcv, args, loc ->
    val typed = wrapAsRuntimeValue(rcv).convertToKotlin(receiverKotlinType, loc)
    wrapAsRuntimeValue(dispatch(typed, convertArgs(name, args, paramSpecs, loc), buildCallInfo(rcv, args, loc)))
}
```

(Receiver conversion target differs from the dispatch key — `StringValue`→`String`, `Function1`→`PatternMapperFn` — so
pass `receiverKotlinType` explicitly; for `useConvertToKotlin = false` cases use a cast-only variant where `rcv` is
passed raw and cast in the dispatch lambda.)

**c) Rewrite the two verbose emitters** in `klangscript-ksp/src/main/kotlin/RegistrationModel.kt` —
`ArityDispatchItem.renderRegistration()` (lines 83–192) and `FileLevelExtItem.renderRegistration()` (lines 268–354) — to
emit a helper call plus a minimal dispatch lambda. No-defaults case becomes ~3 lines:

```kotlin
builder.registerExtMethodFast(cls, "firstOf", < specsExpr >, SprudelPattern::class) { r, a, callInfo ->
    (r as SprudelPattern).firstOf(
        n = a[0] as Any,
        transform = a[1] as ((SprudelPattern) -> SprudelPattern),
        callInfo = callInfo
    )
}
```

Has-defaults case keeps the existing arity `if (a.size >= n) … else …` chain **inside** the dispatch lambda, reading
from the pre-converted `a` and using `a.size` — no inline `convertArgToKotlin`/`CallInfo`/`checkArgsSize`. Reuse
`castSuffix` (applied to `a[i]`), `joinCallArgs`, `withCallInfo`. Per-arg cast types (distinct from `kotlinType`) stay
in the generated dispatch where the precise type is known. Leave `FixedMethodItem`, `VarargItem`, `RawArgsItem`,
`RawBlockItem` as-is.

### Behavior-preservation checklist

- Required count `specs.count { !isOptional }` must equal today's `count { !hasDefault }`.
- Per-arg `nullable` now from `spec.isNullable` (emitted, verified) instead of the inline arg.
- Error messages keep the script function name.
- `CallInfo` only built for functions that use it.
- Varargs untouched (they use `VarargItem`).
- Named-arg resolution unaffected (`paramSpecs` still passed through).

### Expected result

~28-line closures → ~3–6 lines; ~2.4 MB → ~0.8–1.2 MB. **Saves ~1.2–1.6 MB off the 9.3 MB main bundle** (~13–17%),
unconditional (this is always-needed stdlib dispatch, no UX tradeoff). Bonus: 66k → far fewer generated lines speeds
compilation.

## 2. CodeMirror async loading — answer & analysis (~0.55–0.65 MB)

**How much would loading CodeMirror async (like the Kraft addons) save off the initial bundle?**

**~550–650 KB** — the measured `@codemirror/*` (≈421 KB) + `@lezer/*`/`@marijn`/`style-mod`/`w3c-keyname` (≈147 KB)
footprint, ≈6–7% of the 9.3 MB. (These are npm packages that ship clean source maps, so attributed ≈ actual minified.)

**Why it's currently in the main bundle even though a dynamic loader exists:**
`klangscript-ui/.../codemirror/CodeMirrorModules.kt` already does `js("import('@codemirror/state')")` (the same
dynamic-import pattern the Kraft pixi/three addons use). BUT the external declarations in
`klangjs/src/jsMain/kotlin/codemirror/ext/*.kt` are annotated **`@file:JsModule("@codemirror/...")`** (9 files: State,
View, Commands, Language, LangJavascript, BasicSetup, Lint, Autocomplete, LezerHighlight). A `@file:JsModule` is a *
*static** import; webpack puts the module in the main bundle and the dynamic `import()` then just resolves to the
already-bundled copy. The split never happens.

The Kraft addons avoid exactly this — `ultra/kraft/addons/pixijs/.../js/pixi-definitions.kt` even notes _"The JS library
is loaded dynamically — no static @JsModule import"_ — which is why pixi/three land in lazy chunks (235/248).

**What it would take:** remove `@file:JsModule`/`@file:JsNonModule` from the 9 `klangjs/codemirror/ext/*.kt` files and
access every CodeMirror symbol through the dynamically-imported module objects returned by `CodeMirrorModules.load()`
instead of the static `external class` companions (`EditorState.create(...)` → `modules.state.EditorState.create(...)`,
etc.). That re-touches the consumers that use the static classes directly:
`klangscript-ui/.../codemirror/{CodeMirrorComp, CodeMirrorTheme, DslCompletionSource, DslEditorExtension}.kt` and
`src/jsMain/kotlin/codemirror/CodeMirrorHighlightBuffer.kt`, and any editor mount must `await` the load before
constructing the view.

**Caveat on the benefit:** the savings come off the *initial download*, but Klang is a live-coding app where the editor
is the primary surface shown on load — so the ~0.6 MB is needed almost immediately. Async loading therefore **defers**
rather than **eliminates** the cost: the app shell (header/controls) paints sooner and the main bundle parses faster,
but time-to-editable is roughly unchanged. It is a real win for first paint and for any route that *doesn't* show the
editor (e.g. a landing/credits page), a smaller and more conditional win than §1, and a meatier refactor (loses some
static type ergonomics).

## 3. Optional — source maps in the production dist (~21 MB on disk, 0 KB initial load)

`build.gradle.kts:53` sets `devtool = "source-map"` in `commonWebpackConfig`, which applies to production too, emitting
external `*.js.map` (16 MB for the engine alone). Browsers fetch these **only when devtools is open**, so they do **not
** affect end-user initial load — but they bloat the deploy. If deploy size matters, switch the production webpack to
`hidden-source-map` (or stop shipping `.map`). Low priority; no user-facing speedup.

## Recommended sequencing

1. **§1 generated-registration de-bloat** — biggest, unconditional win (~1.2–1.6 MB), self-contained (3 hand-written
   files + 2 processor emitters), no UX tradeoff. Do this first.
2. **§2 CodeMirror async** — ~0.6 MB, improves first paint; do if the extra split + refactor is worth it, especially
   valuable once there is a non-editor landing route.
3. **§3 source maps** — only if deploy size is a concern.

Combined §1 + §2 ≈ **1.8–2.2 MB off the initial 9.3 MB (~20–24%)**.

- Done: `sourceLocationOf` (the June `extractLocation`) and the shortened owner references, both in a8954259
  (2026-09-09). The `firstOf` sample in §1 above is out of date for that reason, and its line references are now

- Not done: everything else in §1.
- The ladder itself (4ad1eb68, 2026-03-29) is older than this task. What the June analysis did not see: since the

### The "No cast needed" warnings

26 warnings, all in generated files, all the same cause (the only other warning in the run is an unchecked cast in
`sprudel/src/commonMain/kotlin/lang/lang_tempo_ply.kt:268`, hand-written, out of scope):

```
GeneratedStdlibRegistration.kt:1880:144 No cast needed.   Katalyst compressor(lookahead: Double? = null)
GeneratedStdlibRegistration.kt:1939:141 No cast needed.   Katalyst limiter(lookahead: Double? = null)
GeneratedSprudelRegistration.kt:799:139, 800:137, 803:139     sine(from: Number? = null, to: Number? = null)
GeneratedSprudelRegistration.kt:830:139, 831:137, 834:139     cosine(...)
GeneratedSprudelRegistration.kt:861:139, 862:137, 865:139     saw(...)
GeneratedSprudelRegistration.kt:892:139, 893:137, 896:139     tri(...)
GeneratedSprudelRegistration.kt:923:139, 924:137, 927:139     square(...)
GeneratedSprudelRegistration.kt:954:139, 955:137, 958:139     perlin(...)
GeneratedSprudelRegistration.kt:988:139, 989:137, 992:139     berlin(...)
GeneratedSprudelRegistration.kt:1067:139, 1068:137, 1071:139  rand(...)
```

Each is `convertArgToKotlin(..., cls = Number::class, nullable = true, ...) as Number?` (or `Double`). The function
returns `T?`, so with `cls = Number::class` the value already is a `Number?`. The generator did not change:
`castSuffix` (`RegistrationModel.kt:372`) has always skipped only `Any?`, and until recently every nullable optional
parameter was `Any?` or a function type (whose cast is needed). The first doors with a nullable concrete type were
the Katalyst `lookahead: Double? = null` (520801eb, 2026-09-27, 2 warnings) and the signal objects'
`from`/`to: Number? = null` (82cc6024, 2026-10-05, 24 warnings).

Fix, at the emission site: `castSuffix` also gets the class-literal type and returns `""` when the parameter is
nullable and the cast type without `?` equals that class literal (`Number?` with `Number::class`). Exact string
equality only, so generic types (`List<Double>?` with `List::class`), type aliases and function types keep their
cast. A non-null `as Number` on the `Number?` result stays, it is a real cast and does not warn. The same rule holds
in every option below.

### Options

Example: sprudel's `duck(orbit, depth, attack)`, three optional `Any? = null` parameters. Today 4 branches, 6
conversions, 4 calls (the shape in the maintainer's question). Sizes: source measured on the prototype, JS modeled.

**(a) Hoist each conversion once, keep the ladder of calls.**

```kotlin
val orbit = if (args.size > 0) convertArgToKotlin(fn = "invoke", args = args, index = 0, cls = Any::class, nullable = true, loc = loc) else null
val depth = if (args.size > 1) convertArgToKotlin(fn = "invoke", args = args, index = 1, cls = Any::class, nullable = true, loc = loc) else null
val attack = if (args.size > 2) convertArgToKotlin(fn = "invoke", args = args, index = 2, cls = Any::class, nullable = true, loc = loc) else null
wrapAsRuntimeValue(
    if (args.size >= 3) duck.invoke(orbit = orbit, depth = depth, attack = attack, callInfo = callInfo)
    else if (args.size >= 2) duck.invoke(orbit = orbit, depth = depth, callInfo = callInfo)
    else if (args.size >= 1) duck.invoke(orbit = orbit, callInfo = callInfo)
    else duck.invoke(callInfo = callInfo)
)
```

- Saves: sprudel 50,138 to 47,326 lines (-173 KB source), libs 12,321 to 11,770 (-38 KB). JS about -90 KB: the
  conversions go, but the calls with their `$default` sentinels stay.
- Runtime: one size check per optional parameter more, no allocation.
- Risk: none for messages and order. Wart: a non-null optional parameter (`n: Int = 1`) becomes `Int?` after
  hoisting and needs `n!!` at the call (149 sites today).
- Complexity: small, but it keeps the O(n^2) call text and the ladder machinery.

**(b) One call, the literal default pasted, no ladder.**

```kotlin
wrapAsRuntimeValue(
    duck.invoke(
        orbit = if (args.size > 0) convertArgToKotlin(fn = "invoke", args = args, index = 0, cls = Any::class, nullable = true, loc = loc) else null,
        depth = if (args.size > 1) convertArgToKotlin(fn = "invoke", args = args, index = 1, cls = Any::class, nullable = true, loc = loc) else null,
        attack = if (args.size > 2) convertArgToKotlin(fn = "invoke", args = args, index = 2, cls = Any::class, nullable = true, loc = loc) else null,
        callInfo = callInfo,
    )
)
```

The `else` is the parameter's own Kotlin default, the literal text KSP already extracts for the thunk
(`safeDefaultThunk`). A non-null one reads `n = if (args.size > 1) convertArgToKotlin(...) as Int else 1`.

- Saves: sprudel to 47,261 lines (-254 KB source), libs to 11,722 (-54 KB). JS about -380 KB (the 445 ladders,
  501 KB today, modeled at about 120 KB).
- Runtime: n size checks, n conversions, one direct call, no `$default` stub. Equal to or cheaper than today's top
  branch, which is what every script call runs.
- Risk: messages and locations identical (each conversion keeps its exact text: `fn`, index, class, nullable, loc);
  order identical (required parameters first, as today, then optional ones by index); named arguments untouched
  (`paramSpecs` and thunks do not change). The default: the literal is pasted where the expected type is the
  parameter's own, so it types as Kotlin's default does (`x: Any? = 3` gets `Int` 3, as the ladder's lower branch
  gives today). Note that a script call already receives the thunk's value today, not Kotlin's
  (`wrapAsRuntimeValue(3)` arrives as `Double` 3.0 in an `Any?` slot), and (b) keeps that difference exactly where
  it is. `DefaultValueExtractor` is already load-bearing for every script call; (b) makes it load-bearing for the
  function-slot path too.
- Non-literal default (the `Slots.*` case of the guardrail): nothing to paste. Two ways, a maintainer decision:
  (i) make it a KSP error for every optional script-door parameter without a safe literal default. That extends the
  error `checkTrailingLambdaShape` already raises for floatable shapes to all shapes, turns the guardrail "Script-door
  defaults must be safe literals" into a build check, and lets both ladder emitters go (zero doors need them today).
  Or (ii) keep the ladder for such doors only: a code path with no live user and no test input.
- Complexity: negative. The level loop in `ArityDispatchItem` and `FileLevelExtItem` goes; `ResolvedParam` gains the
  default literal it already has elsewhere.

**(c) (b) plus three small runtime helpers in `klangscript` (`runtime/NativeInterop.kt`), shared by every module.**

```kotlin
val callInfo = callInfoOf(receiver, args, loc)
checkArgsSize(fn = "invoke", args = args, expected = 0, location = loc)
wrapAsRuntimeValue(
    duck.invoke(
        orbit = optArg(args, 0, Any::class, loc),
        depth = optArg(args, 1, Any::class, loc),
        attack = optArg(args, 2, Any::class, loc),
        callInfo = callInfo,
    )
)
// and in the specs: ParamSpec(name = "orbit", ..., default = NullDefault)
```

- `optArg(args, index, cls, loc): T?`: for the common "nullable, default `null`" parameter; returns null when the
  argument is absent, else exactly what `convertArgToKotlin` does after its bounds check (`NullValue` to null,
  otherwise `convertToKotlin(cls, loc)`), so messages and locations stay identical (the bounds error is unreachable
  on both paths, and `fn` only appears in it). Other cases keep (b)'s `if`. No default parameters on the helper:
  Kotlin/JS would pass the 24-byte sentinel per omitted argument.
- `callInfoOf(receiver, args, loc)`: the five-line `CallInfo(...)` block, once (the June `buildCallInfo`).
- `NullDefault`: one shared `() -> RuntimeValue` for the 882 `{ wrapAsRuntimeValue(null) }` thunks.
- Saves on top of (b): sprudel to 42,989 lines / 2,925,781 bytes, libs to 11,706 / 680,291. JS about -40 KB
  (`optArg`), -130 KB (`callInfoOf`), -125 KB (`NullDefault`); with (b) about -675 KB in all.
- Runtime: `optArg` is a plain top-level function, no lambda, no allocation. `callInfoOf` makes the same two
  allocations as today (the `CallInfo` and its location list), only in one place. `NullDefault` removes 882 thunk
  objects created at registration. No new per-call cost.
- Complexity: three public functions in one file, each a few lines.

**(d) The docs map in its own generated file.** Kotlin/JS starts every function of a file that has a top-level
property with an initializer with that file's `_init_properties_...()` call. The only such property in each
registration file is `val generated*Docs` (`buildMap { ... }`). Emitting the docs functions and that `val` into a
second file (`Generated*Docs.kt`) removes the 2,881 calls from the closures: about -165 KB JS, one function call
less on every door call, a few lines in the generator.

**(e) A `KlangType` table in the docs.** 5,246 `KlangType(...)` constructions, 208 distinct. Emit each distinct type
once as a private `val` and refer to it: sprudel source 2,925,781 to 2,137,002 bytes on top of (c) (97 distinct
types), libs 680,291 to 566,021 (109). JS modeled at about -900 KB (968 KB today minus a 35 KB table minus the
references; if Kotlin/JS renders each reference as a getter call, still about -850 KB). Fewer objects at startup
(5,246 to 208). Done where the text is emitted (the six `KlangType(` sites in `KlangScriptProcessor.kt`, around
lines 1230, 1355, 1487, 1695, 1734, 1771), not as a pass over the output, as a8954259 established. This is the
single biggest lever, bigger than the whole dispatch question.

Modeled sum (b) + (c) + (d) + (e): about 1.7 MB off 9.50 MB (18 %). June's estimate for §1 was 1.2 to 1.6 MB.

### Recommendation

(b) with the cast fix, and (i) for non-literal defaults, as the one generator change; the three helpers of (c) as
the one runtime file in `klangscript` that sprudel, klangscript-libs and any future module share. Reasons: it is
the direct answer to the question, it removes generator code instead of adding any (the stone rule), it costs
nothing per call, it keeps messages, locations, order, named arguments and Kotlin's defaults identical by
construction, and it takes about 0.67 MB (modeled) off the bundle. (i) is a rule change and needs the maintainer;
with (ii) instead the saving is the same today, and the ladder code stays as an untested fallback.

Next, separately: (d) and (e). They are cheap, generator-only, and (e) is worth more than everything above.

### What changed

- **The split.** A library's registration is written as one file per source AREA: the source file's name cut after

  no top-level state. A file-level extension method is its own block, so it lands in its own file's area.
- **Order kept.** The blocks are collected exactly as before and cut into chunks of one area; the entry point

symbols in the order `Resolver.getSymbolsWithAnnotation` returns them, which follows the raw directory listing of
the source folder: sprudel's objects register as `distort crush coarse | cull | gain pregain pan velocity | orbit duck
| notch notchCurves | sine ...`, exactly the `ls -U` order of `sprudel/src/commonMain/kotlin/lang/`, not alphabetical.
ext4 orders a directory by a hash with a per-file-system seed, APFS returns sorted names. So another machine (or a
fresh clone) can produce a different registration order, different chunk boundaries and `...ChunkN` numbers in every
area file, and a different `ktN` numbering in the docs file. "Registration order identical to before" holds on the
machine that produced both outputs; it is not reproducibility across machines. It is also why the areas interleave
(about 150 alternations in sprudel, hence the 150 chunks).

Proposed fix: sort each collected list once by (source file path, declaration position) before generation. That
makes the output reproducible and groups the areas (sprudel back to about 50 chunks), but it changes the
registration order once, which the step 2 brief froze. Today no name repeats within a library, so no lookup depends
on the order. Needs the maintainer's yes.
